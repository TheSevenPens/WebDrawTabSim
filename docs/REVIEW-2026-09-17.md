# WebDrawTabSim: reliability, desktop readiness, and product direction

Reviewed 2026-09-17, against commit `3f0e3b9`.

## Assessment

This is a useful, focused teaching instrument with a viable foundation. Keep the procedural models, the separation between physical pen pose and reported cursor position, the annotation system, and the existing browser renderer. The best next investment is making a demonstration a reproducible document: explicit state, explicit coordinate conventions, deterministic playback, and saved scenes with verification fixtures.

I would not start with a wholesale Avalonia rewrite. First make the current simulator testable and reproducible. Then prototype an Avalonia host that keeps Three.js and provides local file access and integration with recorded-stroke tools. Decide whether to replace the renderer only after measuring a representative workload.

The main engineering weakness is hidden coupling rather than lack of files. The companion modules divide the source visually, but all extend the same mutable `Pen3DSim` object. UI state is copied into that object through many individual setters, and animation paths update both copies differently. This already produces observable inconsistencies.

## What I verified

- Read the application, simulation, geometry, animation, export, controls, documentation, and deployment code.
- Installed the existing npm lockfile with install scripts disabled; the production build passed using Vite 5.4.21. Output JavaScript was 650.91 kB, 171.30 kB gzip, with the standard large-chunk warning. This warning alone is not evidence of poor interactive rendering performance.
- Opened the local app, inspected the rendered demonstration, and exercised numeric controls and animation.
- Reproduced the zero-offset and disabled-azimuth bugs in the browser.
- Invoked actual simulation methods in Node with minimal scene objects to confirm the pen-top-line visibility bug and failure to restore renderer state after an injected export error.
- No browser console errors were returned during those inspected interactions.

This was not a comprehensive hardware benchmark, accessibility audit, dependency-security audit, or image-export qualification. I did not validate a saved PNG pixel by pixel, test clipboard behavior across browsers, or test an Avalonia implementation. Performance recommendations below are hypotheses to measure. No application source was changed; this report is the review deliverable.

## Fixes to make first

### 1. P1: entering zero can silently change a parameter to its minimum

**Evidence:** `src/lib/SliderControl.svelte:35` uses `parseFloat(...) || min` when the number field loses focus. Zero is falsy.

**Reproduction:** Open Pointer tracking, enter `0` in Cursor X offset, then press Tab. The field and slider become `-120`. I reproduced this in the browser. Cursor Y offset and edge attraction use the same component with negative minimums and have the same failure mechanism. Values that round to zero are also affected.

**Consequence:** A neutral mapping can become an extreme mapping while preparing an illustration, without an explicit user change to that value.

**Fix:** Check numeric validity explicitly; never use truthiness as numeric validation. Keep editing text separate from committed numeric state. Test zero, negative values, rounding near zero, empty input, and invalid input on blur.

### 2. P2: pose changes override the pen-top-line visibility setting

**Evidence:** `src/lib/sim/Pen3DSim.js:294` directly sets `penLine.visible`, but `src/lib/sim/pen-pen.js:311` overwrites it with `altitude !== 0` on every pose refresh.

**Reproduction:** Disable Pen top line, then change a pose parameter while tilted. The line becomes visible although the checkbox remains off. Confirmed by invoking the actual methods with minimal Three.js scene objects.

**Fix:** Store the user's annotation preference separately from geometric eligibility. Compute visibility as preference AND eligibility in one place. Apply this rule consistently to every annotation and test changes to unrelated state.

### 3. P2: the all-axis animation leaves azimuth disabled

**Evidence:** `src/App.svelte:323` resets altitude to zero and calls `updateAzimuthState()`. Its animation callback updates altitude but does not recompute that derived flag.

**Reproduction:** Run Anim Rot all and let it finish. The browser shows altitude 45 degrees and azimuth 242 degrees, but the azimuth input and slider remain disabled. I reproduced this.

**Fix:** Derive disabled state directly from altitude with Svelte's derived state. Avoid storing a second mutable value for a condition that can be computed.

### 4. P2: pending and active animations have no unified cancellation policy

**Evidence:** `src/App.svelte:158` and `:323` schedule untracked 500 ms timeouts. Main and parameter animations have separate cancel handles; Reset pen and Demo do not cancel either. Source-confirmed control-flow issue; not stress-tested in the browser.

**Failure cases:** Clicking an animation twice before its delay expires queues two starts. Starting a parameter animation during Anim Rot all creates competing writers. Reset can be overwritten by the next animation frame or a pending delayed start.

**Fix:** One playback controller owns the pending timeout, playback clock, and frame request. Define that Reset, Demo, manual editing, and a new animation stop or explicitly replace playback. A generation token is a simple way to make old callbacks inert. Expose play, pause, stop, seek, and dispose through this controller.

### 5. P2 now; desktop prerequisite: no simulator teardown

**Evidence:** `src/lib/sim/Pen3DSim.js:100` starts a permanent RAF loop without retaining its ID. `src/lib/sim/pen-mouse.js:15` attaches anonymous document listeners. `src/App.svelte:218` removes only its document click listener on unmount. There is no `Pen3DSim.dispose()`.

**Consequence:** Remounting the viewer can leave rendering, keyboard listeners, and GPU resources alive. A one-page browser session can conceal this; multiple desktop documents and repeated viewer creation make it consequential.

**Fix:** Add idempotent disposal with explicit ownership of RAF, timers, event subscriptions, OrbitControls, geometries, materials, textures, shadow resources, renderer, and canvas. Shared textures need shared ownership or reference counting rather than indiscriminate disposal. Ensure partial initialization failures clean up too.

**Acceptance:** Repeatedly create and close viewers; ensure input handlers and render loops do not multiply, and resource counts stabilize after warmup. Test two viewers so disposing one cannot break the other's shared texture.

### 6. P2: failed export can leave the live renderer reconfigured

**Evidence:** `src/lib/sim/Pen3DSim.js:498` changes pixel ratio, size, and camera projection before rendering and restores them only on the successful path.

**Verification:** Injecting a render exception leaves pixel ratio at 2 and never calls viewport restoration.

**Fix:** Validate dimensions and use `try/finally` around temporary renderer/camera changes. Handle a missing 2D context and null `toBlob` results. Give export and clipboard failures accurate messages; the current shared catch says “Copy failed” even for export.

**Further hardening:** A 3840×2160 export at 2× supersampling renders 7680×4320. One RGBA8 color buffer alone is about 126.6 MiB, before depth, multisampling, shadows, copies, or encoding. Check device limits and provide a lower-quality retry. For arbitrary export aspect ratios, update orthographic bounds as well as perspective aspect; the existing UI normally supplies the current viewport aspect, so this is primarily a public-API limitation today.

### 7. P2: global Space handling can interfere with controls and lose its release

**Evidence:** `src/lib/sim/pen-mouse.js:34` intercepts Space on the document, prevents default, and disables OrbitControls. It does not exclude inputs/buttons or reset on window blur.

**Likely consequences:** Space can interfere with keyboard control activation. If focus leaves while Space is held and keyup is missed, camera controls remain disabled. These are source-derived risks, not reproduced here.

**Fix:** Scope pen-drag activation to the viewport, respect editable/control targets, and reset interaction on blur, pointer cancellation, and lost capture. Prefer Pointer Events with capture for a unified pen/mouse/touch drag path.

## Architecture that would improve reliability and portability

### Make the model explicit before splitting more UI components

Introduce a versioned `SceneDocument` containing pen pose, device configuration, mapping configuration, annotation preferences, presentation settings, camera, and optional playback references. Keep transient UI state such as open flyouts outside it.

Use a single state transition path. A command updates validated state atomically; pure computations produce derived pose/cursor/annotation data; the renderer applies that result. UI displays the same state. A multi-field pose update should produce one scene refresh, not six setter-triggered refreshes.

The current `reset()` only returns defaults. Rename that helper to `getDefaultPose()` or make reset an actual state transition. Consistent API semantics reduce mistakes by both humans and agents.

### Extract a small renderer-independent core

Suggested boundaries:

- **Domain:** state types, units, validation, device capabilities, coordinate conversions, pose math, cursor mapping, and interpolation. No DOM, Svelte, RAF, or mutable Three.js scene nodes.
- **Playback:** recorded samples, timing policy, deterministic evaluation at a requested time, and commands.
- **Three.js view:** scene construction, mesh updates, cameras, lighting, annotation drawing, and resource ownership.
- **Application:** controls, document management, undo/redo, import/export actions, and status reporting.
- **Host adapters:** browser downloads/clipboard or desktop files/IPC/native input.

Extract pose and cursor math first. Do not introduce a general-purpose engine, plugin system, or ECS for this scene. Simple functions and explicit dependencies are sufficient. The current procedural model is valuable and does not need to become imported mesh assets to be maintainable.

Replace prototype augmentation gradually with imported functions or composed objects. The issue is implicit dependencies and globally patched class behavior, not an assertion that the existing import order currently fails. Keep a stable public facade during extraction.

Add TypeScript at the domain and adapter boundaries first. Types should distinguish tablet millimetres, world millimetres, screen pixels, degrees, radians, and timestamps. Typed records or named conversion functions are more useful than merely changing every file extension. Validate external JSON at runtime too.

### Specify orientation and units precisely

The simulator's `tiltAltitude` is an angle from vertical: zero means upright. Pointer Events `altitudeAngle` is in radians from the surface: upright is π/2. The initial conversion is `leanFromNormalDeg = 90 - altitudeAngle * 180 / π`, but azimuth origins, axis directions, rotation signs, and twist conventions also need an explicit adapter. [W3C Pointer Events](https://www.w3.org/TR/pointerevents3/#pointerevent-interface)

Name the internal quantity `leanFromNormalDeg`, or clearly label the existing convention in the UI and interchange schema. Preserve source values alongside normalized values. The current 0–60 degree lean limit is a teaching-control limit; it should not silently truncate valid replay data. Define behavior at upright and near-parallel poses, including undefined azimuth and nearly parallel surface intersections.

`SCALE = 24` is an artistic scale, not the conversion from inches to millimetres. The current 384×216 mm area is fine as an abstract device, but documentation that calls it 16×9 inches is not physically accurate. Store real device dimensions directly in mm and separate legacy visual scale. Documentation also describes tablet body dimensions that no longer match `TABLET`, and calls +Z “toward the monitor” while the monitor is placed at negative Z. Resolve these against a single coordinate diagram and reference fixtures.

Keep teaching models distinct from measured hardware behavior. The offset, tilt compensation, and edge-attraction formulas are illustrative parameterizations, not verified emulations of a named driver. Positive edge attraction currently repels the cursor; name/sign this clearly. Define what happens when scaling or offset puts the cursor outside the active area: clamp, hide, or deliberately show extrapolation.

### Build a verification kit an agent can use

The most useful protection against a bad port is an executable specification with visual evidence:

1. **Numerical fixtures:** center and corners; upright and four cardinal lean directions; all azimuth quadrants; barrel rotation; hover; mapping stage outputs; angle wrap; invalid input; and missing capability data. Assert that barrel rotation leaves the tip and pen axis unchanged.
2. **Behavior tests:** zero-value editing, reset during pending/active playback, annotation preferences surviving pose changes, mode switches, resize, teardown, and export restoration on failure.
3. **Golden scenes:** saved scene JSON plus expected numeric values and reference images. Include both device modes, perspective/orthographic cameras, close-up nib views, high lean, all annotation combinations that interact, and each export aspect ratio.
4. **Deterministic rendering:** freeze playback and camera damping at capture time, fix viewport/quality/fonts, and record renderer version. Use tolerant image comparisons on a controlled backend; cross-GPU bit-for-bit pixels are not a realistic universal contract.
5. **Cross-language conformance:** if the domain is ported to C#, run the same JSON fixtures through JS and C# before judging renderer parity.

Add PR CI for type checking, focused tests, and a production build. Current CI deploys from master; it is not a PR verification gate. Choose one package manager and lockfile, pin its version, and use frozen installs. The repository has npm and Bun locks while deployment installs with latest Bun. Recheck dependency advisories rather than trusting the count recorded in `FUTURES.md`.

The native range input already supplies its numeric accessibility semantics; the old suggestion to add all `aria-value*` fields is not the primary gap. The adjacent editable number inputs lack accessible names in the inspected browser tree. Label both controls, expose status messages, document shortcuts, and make focus behavior and flyouts usable by keyboard. Add a concise textual scene description.

## Performance: optimize the workload before choosing another renderer

The scene is modest, but repeated work exists:

- The idle RAF loop always renders. Use invalidation-based rendering while retaining frames during animation and OrbitControls damping.
- Multiple setters rebuild pose/cursor/annotation data repeatedly for one logical update. Batch state changes first.
- Annotation updates construct and dispose tube/pie geometries. Reuse buffers or parameterized geometry where measurement shows that this matters.
- Cursor-only settings currently trigger a full pen refresh and mark shadows dirty. Track which outputs actually changed.
- Preserve the existing shadow caching; separate preview and export quality, including shadow resolution and supersampling.
- Test whether `preserveDrawingBuffer` is needed given explicit render-then-capture export. Do not remove it without export regression tests.

Benchmark idle GPU activity, CPU frame time, dropped frames during replay, peak export memory, and repeated document open/close behavior on your intended machine. Include annotation-heavy close-ups and a realistic stroke recording. The 3D backend should be changed for a demonstrated requirement, not an assumption that native means faster.

## Desktop strategy

### Recommended first experiment: Avalonia host with the current viewport

Use native panels, file dialogs, recording-library integration, and document management around a locally packaged web viewport. Start by hosting the whole app to verify packaging, then move controls native if the workflow benefits.

Avalonia documents a `NativeWebView`, JavaScript execution, and messages back to C#. On Windows its documented backend uses WebView2. Platform prerequisites differ, so validate the exact target/runtime combination. [Avalonia embedding web content](https://docs.avaloniaui.net/docs/app-development/embedding-web-content)

Define a versioned message contract such as load document, replace recording, seek, update state, export, and report error. Use validated structured messages and explicit document ownership. Send recordings in batches and let the playback clock evaluate them; avoid a synchronous cross-language round trip for every sample. Package assets and fonts locally, make the Vite base configurable, and restrict the privileged bridge to trusted local content.

**Prototype acceptance:** load a representative recording; scrub it; render a saved reference scene; export a full-resolution image; work offline; handle resize/DPI; and repeatedly open/close documents. Measure latency and memory. This would establish whether the desktop advantages you want require replacing any 3D code.

### Fully native renderer: possible, but a second project

Avalonia's `OpenGlControlBase` supplies rendering lifecycle/context infrastructure. It is not a direct replacement for Three.js scene graphs, geometry generation, materials, shadows, picking, or camera controls. Those capabilities would need a chosen .NET rendering library or implementation. [Avalonia OpenGlControlBase](https://docs.avaloniaui.net/api/avalonia/opengl/controls/openglcontrolbase)

If that route becomes justified, first port the pure domain using shared fixtures, then one reference scene, then annotation and export parity. Preserve the web implementation as a comparison oracle. Do not ask an agent to rewrite UI, coordinate math, playback, and rendering simultaneously.

## Features closest to your documentation workflow

1. **Named scenes and a scene library.** Save exact pose, mapping, camera, annotations, aspect ratio, and rendering settings. This has more immediate value than another isolated visual toggle. Include schema migration and an optional JSON sidecar with every exported image.
2. **A timeline with exact seeking.** Pause at a chosen sample, step forward/back, set in/out points, slow down, loop, and keyframe camera/annotation changes. Export frames at specified timestamps so an overloaded machine cannot alter the teaching sequence.
3. **Close-up and cutaway views.** A linked magnified nib inset, optional transparent pen body, and a sensor/display cross-section expose the tiny relationships that motivated this app. Keep the overview and detail views synchronized.
4. **Before/after comparison.** Two views share pose/time/camera but have separate mapping or calibration settings. Ghost cursors and a labeled displacement vector can explain compensation without switching scenes.
5. **Publication controls.** Transparent background, clean diagram mode, labels with units, scale bars, title/caption presets, camera bookmarks, and batch export. Add JPEG with an explicit background and quality setting if useful; the current implementation offers PNG and PNG clipboard copy.
6. **Undo/redo and a presentation mode.** Group slider drags into one undo action. Hide editing chrome, expose only lesson controls, and provide keyboard stepping through prepared scenes.

Video/GIF output becomes much easier after deterministic seeking. Prefer rendering a known frame sequence for final publications over screen-recording whatever RAF happened to deliver.

## Uses for stylus and drawing-application developers

These are product hypotheses grounded in available input data and common signal-processing questions, not a claim that demand has been validated with users.

### Recorded-input inspection and reproducible bug reports — strongest next direction

Show the 3D pen alongside synchronized X/Y, pressure, tilt, rotation, event intervals, contact state, and buttons. Selecting a chart sample selects the exact pose. A developer can attach a small recording plus scene and say “the discontinuity begins here.”

A recording schema should include source/API, schema version, device dimensions/calibration, timestamps with units and clock origin, sequence numbers, coordinate space, raw values, normalized values, contact/hover/tool state, and capability validity. Pressure, hover distance, and twist are distinct quantities. Do not infer physical hover height from pressure or silently replace an unsupported channel with a measured zero. Windows exposes validity flags for optional pen fields. [Microsoft pen masks](https://learn.microsoft.com/en-us/windows/win32/inputmsg/pen-mask-constants)

Import your existing format first, once a representative recording is available. Preserve gaps and out-of-range samples for diagnosis; do not silently “repair” evidence. Downsampling is a presentation choice, not deletion of original samples.

### Filter, resampling, and prediction laboratory

Replay one recording through raw and processed pipelines. Visualize smoothing lag, corner rounding, overshoot, jitter, report-rate changes, and predicted versus later confirmed trajectories. Pointer Events defines coalesced and predicted samples that could feed this view where supported. [W3C Pointer Events](https://www.w3.org/TR/pointerevents3/)

Report algorithmic displacement and timing with known clock assumptions. A screen animation alone cannot establish physical end-to-end pen latency; that needs independent measurement.

### Mapping and calibration laboratory

Visualize active-area crops, aspect-ratio preservation, tablet rotation, multi-monitor arrangements, DPI coordinate transforms, and absolute/relative mapping. A calibration error field across the surface would make spatial distortion easier to understand than a single global offset.

### Pressure and brush-response laboratory

Add an illustrative brush footprint driven by pressure, tilt, and barrel rotation. Compare transfer curves, dead zones, hysteresis, saturation, and contact thresholds. Make it clear whether the brush is a teaching model or an implementation of a particular engine.

### Event and tool-state laboratory

Inspect hover-to-contact transitions, pointer cancellation, lost capture, barrel buttons, eraser switching, and pen/touch arbitration. These need an event timeline and state machine; they cannot be represented by pose alone. A native capture adapter could compare input APIs where accessible. Simulation can explain palm-rejection policies but cannot reproduce a digitizer's physical sensing behavior without appropriate captured data.

## Further exploration

- **Parallax lesson:** independently show physical tip, sensing plane, reported coordinate, rendered cursor, and observer viewpoint. Vary display-stack thickness and view angle to distinguish optical parallax from calibration and driver offsets.
- **Interactive documentation embeds:** publish a bounded scene with only the controls needed for one explanation. Readers can manipulate the phenomenon instead of only seeing a picture.
- **Synthetic recording generator:** circles, slow diagonals, stops, spirals, orientation sweeps, known jitter, dropped samples, and angle-wrap cases. Export expected outputs for application test suites. Synthetic events do not validate real driver behavior.
- **Regression evidence generator:** run a collection of scenes or recordings against two algorithm versions and produce paired illustrations plus numeric differences.
- **Tilt-driven interaction experiments:** explore orientation-controlled selection or navigation, with a clearly defined prototype task. Existing HCI research provides an adjacent direction, though this is farther from the core documentation workflow. [Microsoft Research: Tilt-Responsive Techniques for Digital Drawing Boards](https://www.microsoft.com/en-us/research/wp-content/uploads/2020/10/Tilt-Responsive-UIST-2020.pdf)

I would keep the product centered on explanation and diagnosis rather than growing it into a general drawing application.

## Recommended sequence and completion criteria

**Stage 1 — Trustworthy current behavior.** Fix the seven reliability issues, correct terminology/documentation, and add focused regression checks. Done when the reproduced bugs stay fixed, resets stop playback, export failure restores the viewport, and teardown is complete.

**Stage 2 — Reproducible scenes.** Introduce typed state, atomic updates, pure pose/mapping functions, saved documents, and golden scenes. Done when loading a scene reproduces its numeric state and intended illustration without manual reconstruction.

**Stage 3 — Useful replay.** Import one real recording format and implement deterministic seek, stepping, validity metadata, and paired numeric/3D views. Done when a specific source sample can be identified and rendered repeatedly without timestamp or orientation ambiguity.

**Stage 4 — Desktop evidence.** Build the smallest Avalonia/WebView prototype that supports local files, one recording, and image export. Done when it meets the actual offline, integration, latency, and memory requirements on your target machine.

**Stage 5 — Expand deliberately.** Add comparison, detail insets, publication automation, and developer diagnostics according to actual usage. Consider a native renderer only if the measured limitations or integration requirements justify its additional maintenance.

For an AI-assisted port, the highest-value handoff is a coordinate specification, versioned sample/scene schemas, a small pure domain API, numerical fixtures, golden images, explicit resource ownership, and acceptance commands. These let an agent prove it preserved behavior instead of relying on its interpretation of a 3D screenshot.
